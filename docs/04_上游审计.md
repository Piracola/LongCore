# 上游项目审计：GaoXanSheng/JiaolongControl

> 审计日期：2026-09-06 · 分支 `windows/X86-64` · MIT 许可 · 本地克隆于 `upstream/JiaolongControl`（已 gitignore）

## 一、总体结论

**协议同源确认，项目可信度较高，可以作为贡献/分叉对象。**
它就是我们逆向出的那套协议的完整实现，且比我们多了 SMU 降压和 EC 直读风扇两条通道。

## 二、架构

```
┌─ Client/  Vue 3.5 + TS + Vite + Arco Design Vue + ECharts + Pinia + Tailwind 4
│    ↕ WebView2 (COM Bridge，非 HTTP)
├─ Server/  .NET 8 WPF 宿主 (MainWindow.xaml.cs 持有 WebView2)
│    ├─ Bridge.cs → 14 个 Controller (CPU/Fan/GPU/Keyboard/PerformanceMode/...)
│    ├─ MethodServices.cs  ← WMI 透传（唯一入口，与我们的协议一致）
│    ├─ Blding64.cs        ← EC 直读（内核驱动 JiaoLongDriver64.sys）
│    └─ PawnIO.cs          ← SMU 访问（PawnIO 签名驱动 + 3 个 .bin 模块）
└─ Drivers/  Blding/ (厂商 .sys+.dll 二进制)  PawnIO/ (RyzenSMU/AMDFamily17/Nvidia.bin)
```

配置持久化为 YAML（`JiaoLongConfig`），5 秒差异落盘。

## 三、三条硬件通道逐条核实

### 1. WMI 透传（与我们的逆向 100% 同源）

`MethodServices.cs`：`root\WMI` → `MICommonInterface.InstanceName='ACPI\PNP0C14\MIFS_0'` → `MiInterface`。
`InData[1]=Get(0xFA)/Set(0xFB)`、`[3]=命令码`、`[4..]=参数`、16 位小端 `(data[5]<<8)+data[4]`——与我们实测协议逐字节一致。

命令枚举（`SysEnums.cs`）与我们反编译的表一致：

| 码 | 它的名字 | 我们的名字 |
|---|---|---|
| 8 | SystemPerMode（Balance=0/Perf=1/Quiet=2）| 性能模式 |
| 9 | GpuMode（Hybrid=0/Discrete=1）| 显卡模式 |
| 10 | RgbKeyboardStatus | 背光 |
| 11-12 | FnLock / TPLock | FnLock / 触摸板 |
| 13 | CPUGPUFanSpeed | 风扇 RPM |
| 15-18 | Ambientlight / Mode / Color / Brightness | 氛围灯/灯效/RGB/亮度 |
| 19 | SystemAcType | 适配器 |
| 20-21 | MaxFanSpeedSwitch / MaxFanSpeed | 强冷/最大风扇 |
| 22 | CPUThermometer | CPU 温度 |
| 23 | CPUPower | CPU 功耗（SPL/SPPT/温度墙）|

**实现差异（可提 PR 的点）**：
- 它不做响应校验（只判 `output != null`）；我们的实现有回显校验，更健壮
- 每次调用 new ManagementObject（性能小瑕疵）

### 2. EC 直读风扇（超出我们逆向范围，安全审计重点）

`Blding64.cs` 加载厂商驱动 `JiaoLongDriver64.sys`（比特兰德"BLD"，仓库内含 33KB .sys + 138KB .dll 二进制）走端口 `0x4E/0x4F`：

- 风扇转速读：`0xC834/0xC835`（RPM）、`0xC836/0xC837`
- 手动转速写：`0xC83C/0xC83D` + 模式掩码 `0xB20 |= 0x02(CPU) / 0x08(GPU)`，恢复自动写 `0xB20=0x00`
- EC 芯片 ID 判定：`0x2000==0x55` 时写 `0x1060|=0x80`；EC 版本 `0xC411`

风险：`DriverLoader` 直接 CreateService+StartService 加载 .sys（错误 1275 已处理提示，即内存完整性开启时会被拦）；EC 直写比 WMI 更底层，误写风险更高。**这些 EC 寄存器地址是本项目最稀缺的知识**——官方控制中心都不用这条路。

### 3. PawnIO SMU（现代安全方案）

`PawnIO.cs` + `RyzenSMU.bin`/`AMDFamily17.bin`/`Nvidia.bin`（namazso/PawnIO.Modules 官方模块），MSR 读写走 `ioctl_read_msr`。与 UXTU 新版同方案，比裸 WinRing0 安全。Curve Optimizer/PBO/TDC/EDC 都在这层。

## 四、功能缺口（= 我们的机会）

1. **热键完全未实现**：全库无 `HID_EVENT20`/`OSDEvents`/`RegisterHotKey`。我们反编译出的完整事件表（`WMIEventName` 4~33）+ 事件监听协议是现成的贡献素材——实现 Fn 快捷键接管/OSD 的唯一缺的资料。
2. 响应校验缺失（健壮性 PR）
3. 性能模式只有 3 档（0/1/2），我们逆向表里还有 AirPlaneMode/CustomMode 等
4. **UI（用户痛点，见第六节）**

## 五、对我们的策略修正

- **Linux 兼顾**：上游有 `Linux/X86-64` 分支（作者已在做 Linux 版），比我们之前判断的更乐观
- **建议组合**：功能/文档/热键向上游提 PR；UI 重设计走我们自己的 fork（作者的个人审美不宜硬改）；EC 寄存器知识整理后可交换验证
- 前端是 **Vue 不是 React**——Composition API 与 React Hooks 相似度约七成，上手成本低

## 六、UI 诊断（对照 Doc/Main.png 截图）

现状：暗紫仪表盘 + 动漫欢迎横幅 + 背景视频。

1. **风格割裂**：二次元横幅与数据仪表气质冲突；`BackgroundVideo.mp4` 常驻播放，信息密度为负
2. **图标隐喻混乱**：树叶=静音、天平=平衡、火箭=高性能，小尺寸难辨认；PNG 图标风格不一（文件名都有中文：`监控.png`、`kuaijiechaxun.png`）
3. **色彩无语义体系**：CPU 71°C 与 GPU 51°C 同为蓝紫色，温度没有警戒色阶（且中文场景下"升温=红"是默认预期）
4. **密度失衡**：欢迎横幅占约 1/3 屏幕，核心操作分散
5. **组件库用得不深**：装了 Arco Design 但大量自绘控件，设计令牌（间距/圆角/字阶）不成体系

**改进路线（低风险 → 高收益）**：
1. 去视频背景、统一图标为线性图标库（Lucide/Tabler）、建立温度语义色阶
2. 用 Arco 主题变量统一间距/圆角/字号；欢迎横幅缩为一行状态条
3. 仪表信息架构重组：性能模式改顶部胶囊切换；监控环加阈值变色
4. 最后做动效与暗色打磨
