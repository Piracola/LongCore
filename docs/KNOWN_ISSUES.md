# 已知问题清单（Known Issues）

> 版本：LongCore 0.1.4 · 2026-09 · 持续更新

## 行为限制（设计如此 / 有意取舍）

1. **浏览器直连预览显示全 0**
   通过普通浏览器访问前端页面时没有 WebView2 桥（`window.chrome.webview` 缺失），
   温度/转速/功耗等数据全部为 0。这是预期行为——完整功能必须在主窗口内使用。

2. **飞行模式（AirPlaneMode）不提供热切换**
   EC 命令 9（显卡模式）写入后必须重启生效，不能作为"模式热切换"处理。
   独显/混合切换保留在设置页（GPUDirectConnection），切换后请手动重启。

3. **"自定义"性能模式是本地逻辑态**
   自定义档（第 4 段胶囊）不写入 EC 模式命令，仅打开命令 23 的自定义功耗子状态；
   实际 SPL/SPPT 数值以 CPU 页保存的配置为准。切回标准档时自动关闭该子状态。

4. **Fn 热键只接管性能模式键（事件 15）**
   其余 Fn 复合键（屏幕亮度/触摸板/键盘灯效等）保持固件默认行为，LongCore 不拦截
   —— 键盘灯效自 2026-10-06 起完全由厂商软件/固件管理，LongCore 不再下发任何键盘 RGB 命令。
   可在设置页整体关闭接管（`App.HotkeyEnabled`）。

5. **应用内曲线接管会绕开 EC 固件温控（有意取舍）**
   固件三档（办公 / 游戏 / 狂飙）下 EC 自带温控表在低负载区把转速压得极低、临近温度墙
   （默认 95℃）才跳变，表现为"平时很静、到墙才猛拉"，其形状无法从软件层改变。
   因此应用内曲线接管在三档下同样生效（`Fan.Enabled`）。代价是写入转速会置位 `0xB20`
   手动掩码，EC 自身温控被绕开，软件成为唯一控制者；兜底为 `ThermalWatchdog`（默认 98℃
   持续 10s 强制 5800 RPM）与 `EcGuard`（进程崩溃后下次启动恢复 EC 自动模式），二者默认开启。
   交还 EC 的入口仍在：关掉曲线开关，或在风扇曲线页点「交还 EC 固件温控」（停曲线服务 +
   `Fan.RemoveFanSpeed` 撤掩码 + 把 `Fan.Enabled` 落盘为 false，避免下次开机自启又把曲线拉起来）。
   2026-10-06 起不再有「手动设定风速档位」这第三种控制权。

6. **曲线接管会产生"转速抖动"，0.1.4 改为温度域抑制**
   实测（2026-09-23，28.5 分钟真实负载）：CPU 风扇**没有一秒是停着的**——88 个采样点
   全部各不相同，102 次方向反转中 95 次幅度只有 100 RPM（每 1~2 秒就改写一次硬件）。

   0.1.3 曾在最终 RPM 上加 300 RPM 死区，**实测无效**，三点原因（均由真机日志
   21:02~21:32 的 1789 个 1 秒样本离线重放确认）：
   - 旧"非对称低通"本身就是噪声放大器。系数 0.25/0.12 的时间常数只有 3~7 秒，而温度计
     每秒抖动 ±2℃（|dT| 均值 0.71℃/s、p99 = 5℃/s —— 这个量级的变化在热质量面前不可能是
     真实温度），于是平滑值摆幅约 ±3℃，比原始读数更大。
   - 死区在转速域：挡得住 100 RPM 的量子抖动，挡不住"被放大后的 ±3℃ × 曲线斜率" = ±400 RPM。
   - 升降斜坡对称（各 600 RPM/s），降温方向同样激进。

   0.1.4 改为三件事（详见 `AutoFanControl.ProcessAndApplyFanSpeed`）：双跟踪器
   （`TempAttackS`=5s 快升 / `TempReleaseS`=60s 慢降；升速目标取**快**跟踪值的曲线点，
   降速目标取**慢**跟踪值）、温度域不灵敏带（`TempHysteresisC`=5℃）、降速每秒最多退一格。
   同一段真实数据离线重放：写入 **88 → 3 次**、方向反转 **36 → 0 次**（30 分钟窗口），
   跟踪值与真值的均值偏差仅 +0.15℃。代价是转速对温度的跟随整体变钝（最多滞后
   一个不灵敏带宽度），因此 90℃ 以上急停段与 98℃/10s 看门狗成为主要的过温兜底。

   同时移除了 CPU→GPU 的 0.85 交叉同步：实测 GPU 仅 56℃ 时其风扇被 CPU 拖到
   3400 RPM（按自身曲线只需 1500~1800），那是零散热收益的噪音源。

7. **日志默认不再记录逐次数据读取**
   旧行为是每次 WMI/EC 读取、每次前端 IPC 调用都写一行 DEBUG，实测一天 5.7 万行
   / 6.4 MB（约 27 次/秒同步写盘），其中 98.4% 出自 `CommandResult` 构造函数。
   现默认 `Log.Level=INFO` 且 `Log.CommandDebug=false`，控制侧信息
   （AutoFanControl 转速、看门狗、EcGuard、写入闸门拦截）一行不少。
   排查读取类问题时可临时打开；三项设置均在设置页，改后立即生效无需重启。

8. **OSD 需要 UI 线程可用**
   Fn 切换模式的屏幕提示经 WPF Dispatcher 显示；若主窗口线程被长时间阻塞，
   提示会延迟出现。窗口最小化到托盘时 OSD 仍可正常弹出。

9. **SMU 限制值不可回读，「重置」不等于「恢复系统默认」**
   SMU 的零值禁写集合是 12 项（10 项限制参数 + 2 项温度墙），它们没有可靠 getter
   （只能确认命令是否被接受），界面因此显示「未读取」
   而不是 0，0 也会被前后两道写入闸门拒绝。由此：SMU 页只对**有明确默认值**的参数提供重置
   —— 曲线偏移=0（不偏移）、逐核 CO/OC=0；温度墙的 99℃ 是**应用推荐值**（页内已如此标注），
   不是固件读回值。功耗/电流限制**不提供重置**：官方控制台没有这些参数的 API 与数值
   （反编译 vendor/decompiled 零命中），配置模型里它们的默认值就是 0（=未读取），
   编一个数字写进固件就是虚假成功。见 v4 §14.4。
   逐核 CO/OC 的处理见下条（写进配置但**不在开机时下发**）。

10. **逐核 CO/OC：记住但不自动下发**（Decision 2026-09-24）
   逐核值写进 `config.yaml`（`Smu.PerCoreCurve` / `Smu.PerCoreOcClk`），重启后 SMU 页把上次
   成功应用的那套填回表单；但**开机不会自动下发**——16 核 × 2 参数 = 32 条 SMU 命令的无人值守
   写入，手误会被每次开机重放，收益不抵风险。要生效仍需在 SMU 页点「应用逐核设置」。
   另外：冷启动后硬件里那份逐核值是否还在（固件重新初始化是否清掉 SMU 寄存器）**未经真机验证**，
   所以页面按"需要时重新应用"表述，不承诺硬件侧的记忆。

## 平台 / 环境相关

11. **必须管理员权限运行**
   EC 驱动加载、WMI 写入、`powercfg` 联动均需要管理员。安装器已配置
   `requireAdministrator`；若直接运行 exe 被拒，请右键"以管理员身份运行"。

12. **WMI 通道抖动**
   响应校验失败会自动重试一次（连续两次失败判定为通道异常并返回默认值）。
   休眠唤醒后首几次读取可能短暂失败，随后自愈；若持续失败请重启应用。

13. **GPU 温度来源依赖 NVAPI**
   NVIDIA 驱动不可用或初始化失败时，GPU 温度沿用该风扇上一次的平滑值，
   **不再回退成 CPU 温度**（2026-09-23 改）。原先的回退会把单调 80~86℃ 的 CPU 温度
   灌给只接一路 GPU 的风扇，与"各自跟随自己温度"的设计相互抵消。
   实测日志中该分支从未触发。

14. **无噪音传感器**
   首页噪音值按风扇转速查表估算（3000 RPM≈25 dBA 标定），仅供参考。

## 版本历史修复（本 fork）

15. **切到 GPU 页偶发卡顿（本 fork 修）** —— 症状是「从别的界面切到 GPU 页会顿一下」，
   切到 CPU / SMU 页也有同样问题但较轻。根因是**页面组件在 setup 顶层 `await`**：
   `GPU.vue` 顶层 `await fetchGpuRanges()`（`Promise.all` 里 7 个 NVAPI 值域调用，其中 3 个
   带 `.catch(() => null)`）、`CPU.vue` 顶层 `await CPU.GetCpuInfo()`（每次进页都跑一次
   `Win32_Processor` WMI 查询，**本轮没有改它**）、
   `RyzenSmu.vue` 顶层 `await fetchConfig()`。顶层 await 让这些页面成为 **async setup 组件**，
   `RightSide.vue` 的 `<Suspense>` 必须等它们全部 resolve 才挂载新页。

   ⚠️ **观感要更正**：切页时用户看到的**不是** Suspense 的加载圈。实测（vue 3.5.42）：
   首次挂载才走 `ssFallback`；切页时 `isInFallback === false`，新页在**离屏容器**里构建，
   **旧页继续显示**直到新页就绪。体感是「旧页僵住不动」，不是「转圈」
   （若没有 Suspense 则更糟——会是空白占位）。

   改法：去掉全部顶层 await，改成 `void (async () => { ... })()` 后台补齐，首屏立即出、
   数据到位后自行填上。`fetchConfig(force=false)` 自带两道短路——「已有值不重拉」与
   in-flight 去重（`config.ts:26,28`），`App.vue` 启动时已在拉。⚠️ 但 `config-changed`
   事件走 `refresh()` → `fetchConfig(true)`，**会绕过这两道短路**；本页的兜底调用不影响它。

   ⚠️ 去 await 会把「配置到达」从 setup 同步期挪到后台，**两个依赖配置已在位的同步初始化
   必须一起挪进同一个 IIFE**，否则静默退化成假读数：
   - `RyzenSmu.vue` 的分组快照 `snapshotGroup()`：它内部有 `if (!smuData.value) return`，
     留在 setup 同步段会空跑 → 快照永远种不下 → 用户改了滑条，状态条恒显示「无改动」。
   - `RyzenSmu.vue` 的 `watch(coreCount, …)` 原先只依赖 `coreCount`；`GetPhysicalCoreCount`
     与 `fetchConfig` 都是桥接调用、到达顺序无保证，前者先回时逐核表会**永久填 0**
     （0 是合法值，界面上没有任何「未读取」提示）。故改为同时 watch 配置里的逐核值。
   - `GPU.vue` 的基准快照 `captureBaseline()`：用户在值域探测往返期间拖了滑条时，
     此时取基准等于把「尚未下发的意图」当成已应用 → 状态条谎称无待应用。
     故加 `if (userTouched.value) return`（宁可不落基准），并让 `applyStatus` 在基准为
     null 时像 CPU 页的 `neverApplied` 那样说「尚未应用」而不是「配置已存盘」。
   - `CPU.vue` 的「改参数即存盘」watch **原本没有 userTouched 守卫**。这不是它自己的 bug，
     而是去 await **新暴露**的：改造前顶层 await 让配置在 setup 期就位，watch 注册时不触发；
     改造后配置从 undefined 变成有值这一跳本身就会触发，于是「只是浏览 CPU 页」就落一次盘。
     已按 GPU.vue 同一套语义补守卫（五个滑条 `@change` 置位）。走「应用」的保存不受影响
     ——那条路径由 `cpuPowerPlan.ts` 显式 `saveConfig()`，不依赖该 watch。

   同轮清掉两条慢 WMI 查询（都要经宿主 UI 线程，缓存的是进程生命周期内不变的常量）：
   `NvidiaGpuController.GetGpuDriverDate` 的 `Win32_VideoController`（本仓最慢的 WMI 类；
   该通道前端另有 30s TTL，原为每 30 秒穿透一次，不是每 5 秒）与
   `CpuController.GetBaseFrequency` 的 `Win32_Processor`（该通道 TTL 仅 1s，原为每 5 秒
   一次，是这两条里收益更实的一条）。两者改为按进程缓存；**异常不填充缓存**（WMI 抖动可
   自愈），只有"查询成功但无匹配"才永久缓存。

16. **CPU 电压读数取的是伪值（VID 位域错，2026-10-06 修）** —— `RyzenSmuController.ReadVidVoltage`
   读 `MSRC001_0293`（`0xC0010293`）后用 `(raw >> 6) & 0xFF` 取 VID，但该 MSR 的位域是
   `CurCpuFid [7:0]` / `CurCpuDfsId [13:8]` / **`CurCpuVid [21:14]`** / `CurHwPstate [24:22]`。
   `>>6` 取到的是 DfsId 高 6 位 + Fid 高 2 位的**混合字段，随主频跳变、与真实电压无关**。
   换算式 `1.550 - vid * 0.00625` 本身是对的（与 LibreHardwareMonitor 的 `Amd17Cpu.cs`
   逐字一致），错的只有位移。已改为 `>> 14`。

   这个 bug 长期没暴露，是因为 `volts is >= 0.4 and <= 1.8` 的范围校验会把大量伪值挡掉返回
   `null`，于是**静默回退**到 WMI/LHM 读数 —— 用户看到的是"时好时坏"，很难归因。

   ⚠️ **修正未经真机验证**：需要管理员权限跑 `RyzenSmuControllerTest --vid-per-core`，与
   CPU-Z / HWiNFO 的 Vcore 对照。该命令现在**同时打印修正位移（`>>14`）与旧位移（`>>6`）**
   及原始十六进制，一次跑完即可对照。修正后 CPU 页电压数字会变（这正是修复的目的）。

   同轮把「`Environment.ProcessorCount` 个逻辑核全扫取 min」降为「4 核均匀采样取平均」。
   降开销的同时**语义也变了**，理由：VID 是随负载实时变化的瞬时量、不是体质指标，
   而 `ProcessorCount` 是**逻辑**核数（16C/32T 上 SMT 兄弟共享同一物理核的 VID），
   原来的 `minVolts` 实际≈"扫描瞬间最闲的那个核"，既不是最坏情况也不是平均值。

17. **性能模式枚举错位**（上游遗留）：前端 TS 枚举顺序与后端 C# 枚举不一致，
    上游靠页面"错位命名"掩盖。0.1.0 起前后端枚举已对齐（Balance=0 / Performance=1 /
    Quiet=2 / Custom=3）。

18. **EC 高频重复写入**（上游遗留）：自动风扇控制环曾以固定 1s 周期无条件重写 EC。
    现已加入同地址同值 300ms 去重节流与写入地址白名单。

19. **崩溃后风扇状态残留**（上游遗留）：进程硬崩溃时手动风扇模式可能残留在 EC 中。

- **风扇曲线在设定温度区间不生效（降速退不下来）—— 真机 A/B 已确认修复**：
  同一台机器、同一条曲线（`config.yaml` 20:40:20 保存）、同一个温度带：
  - 旧构建 `20:50:46 84.9℃/4900` → `20:54:37 76.9℃/4800`：降 8.0℃ 只退 **100 RPM**；
  - 新构建（日志带 `| 查表温度` 字段起）`21:01:47 77.4℃/5000` → `21:02:19 77.3℃/1800`：
    32 秒内**每秒退一格**，正好停在曲线值 1800（65–80℃ 平台段），期间慢跟踪值还略回升，
    说明降速段一旦进入就不再依赖门槛反复触发。
  根因：降速段每退一格都要重新过 `FallGateC` 降温门槛，而每次写出都会刷新锚点
  （`ApplyFanSpeed` 里的 `LastDecisionTemp`），于是退化成"每 `FallGateC` 度才降 100 RPM"。
  修法：新增显式"降速段"闩锁 `FanState.Descending` —— 门槛只负责**进入**，进入后每秒退一格
  直到追上当前温度对应的曲线目标（`AutoFanControl.cs` 的 `ProcessAndApplyFanSpeed`）。
  同时新日志行会在查表温度与锚点不一致时附 `| 查表温度: xx.x°C`：升速段两者按
  `20:59:31~21:00:34` 的数据反推相差 1.4~3.9℃，缺这一段会让"日志 80℃ 却给 4500 RPM"
  看上去像曲线没生效。
  ⚠️ **另外两条"曲线不生效"是审查挖出来的，同轮一并修（只过了模型验证，真机待验）**：
  1. **改配置不当拍生效**：温度平稳时两个温度域门槛都不满足，旧实现可以几分钟不写一次硬件
     —— 用户在曲线页拖动存盘后**看不到任何反应**（`20:39:44~20:42:52` 那三分钟正是如此）。
     现加"风扇配置指纹"（`FanConfigFingerprint`，只覆盖曲线/噪音档/合并开关/两个时间常数），
     指纹变了的当拍按 `curve(快跟踪值)` 重算一次，仍过安全下限。模型验证：死平 78℃ 下把
     80℃ 点从 1800 调到 1500 → 当拍写 1500；调到 4200 → 当拍写 3900（= `curve(78℃)`）。
  2. **尖峰后的"永久高转速"**：升速目标取快跟踪值、降速锚点取慢跟踪值，10 秒尖峰能让快值到
     93.6℃→5600 RPM 而慢值只到 ~87℃；温度回到 86℃ 平住后锚点也停在 86℃，"低 8℃"永不成立
     → 风扇永久高出曲线 1200 RPM（模型里 900 秒不写一次硬件）。现加"偏离存活期"
     （`InSustainedExcess`：转速持续高出当前曲线 800 RPM 达 60 秒即允许进入降速段）。
     模型验证：95/92/100℃ 尖峰后平台终值都落到曲线的 4400 RPM（旧判据分别是 5600/5300/5800）；
     **降温快于 0.13℃/s 时行为逐字不变**（先由 8℃ 门槛触发，27 次写入、每步 −100 完全一致）；
     转速已等于曲线值时 300 拍零多余写入。
  3. 顺带修掉 `CalculateFanSpeed` 的退化段除数：手改 `config.yaml` 造出重复温度点会算出

  带 `查表温度` 的 30 条记录里 29 条 `curve(查表温度) == 日志 RPM`，唯一偏差是一次四舍五入），

  ① `Controller.step()` 逐字复刻了上面那个降速退化（`:309` 的门槛 + `:322` 的复位），

- **从自定义档切出时可能被顶回"进入自定义前的那一档" —— 修复未真机复现**：
  观测（`:331-335`）：`20:38:39,993 写入 8` → `20:38:40,018 写入 23` → `20:38:40,021 写入 23`
  → `20:38:40,024 事件 QuietMode` → `20:38:40,042 事件 BalanceMode`。注意**日志不记录写入载荷**
  （`MethodServices` 只打响应字节，载荷只在 DEBUG 级），"写入 8 是办公"是由紧随的 QuietMode
  事件推断的。同一天另一次切出（`20:39:32`，`:367`）只出现一次事件、没有回退 —— 这是**间歇**
  现象，不能写成"必失败"。
  规律（全日志"自定义确实开着时关 23"共 **5 簇，5/5 自洽、0 反例**）：关命令 23 会把固件档位
  退回**进入自定义前的那一档**，且只有"退回值 ≠ 刚写入值"时才补抛一次档位事件 ——
  于是刚写好的档位被顶掉：`19:00:28`/`19:00:31` 退回的是**狂飙（Performance）**、
  `20:38:40` 退回的是**游戏（Balance）**；而 `01:37:24`/`20:39:32` 的退回值与刚写入值相同，
  就没有第二次事件。"本来就已关再关"（6 簇单次关闭）是无状态跃迁，全部无后续事件。
  机制仍是**推断**：日志不记录载荷，`cmd 8` 当时回读成什么也无从得知，未经真机确认。
  修法（对上述解释与"命令 8 在自定义子状态下被事后覆盖"两种解释都成立）：
  `PerformanceModeController.Set()` 改为**先关命令 23、有界轮询到 EC 真的报告已关、再写命令 8**，
  写后回读一次，只有**明确读到别的档位**才补写一次。这样"关子状态引起的任何档位回落"都发生在
  目标档位写入之前，不会被覆盖。前端 `mode.ts` 的 `applyHotkeyMirror` 在 `syncing` 期间不再
  改写状态：那两次事件里至少有一次是我们自己的写入触发的，采信中间态会让写后回读判据看到假值。
  参考（只是**顺序意图**，不是等价实现）：官方在热键事件路径里也是先收敛自定义子状态、再刷新
  档位表现（`vendor/decompiled/main.cs:2182-2184`；其中 `SetAP_PerformaceMode` 只刷 UI，
  真正写命令 8 的是异步的 `SetSP_PerformaceMode`，`:1825-1830`），官方点预设按钮时并不关自定义。
  ⚠️ **回读判据留在前端**：服务端只做"尽力收敛"，回读不一致时返回 `Success=true` +
  「命令已被接受，但回读未确认」—— 报 `false` 会让前端走 failed 分支并**跳过**那次权威的写后
  独立回读（`mode.ts` 的 `if (accepted)`），把 documented 的 `accepted` 降级成 failed（契约见
  AGENTS.md §模式约定）。
  ⚠️ **适用范围与待查**：本不变量只覆盖 `PerformanceModeController.Set()`。命令 8 在全仓只有
  该文件两个写入点；`ApplyMirrored`（Fn 路径）、`SelfStart.cs:41`、`CpuController.cs:68/72` 都只
  开/关命令 23、不写命令 8。若"关 23 会退回旧档"成立，Fn 路径在同一场景下缺少纠正手段 ——
  需真机在自定义态按一次 Fn+Q，看是否出现两个事件、最终停在哪一档，再决定要不要补收敛
  （见下条第 24 项）。
  ⚠️ **晚投递窗口（未修）**：`syncing` 守卫挡不住"事件在 `syncing` 结束之后才被 JS 处理"的
  情况，此时 UI 可能显示退回的旧档而硬件在目标档；全仓没有周期性的档位刷新兜底
  （`App.vue` 只启动补一次、`Home.vue`/`CPU.vue` 只在进入页面时）。真机若观察到"切完过一会儿
  胶囊自己跳回旧档"，按这个方向查。
