## 1. 为什么要做（Observation，均带 `文件:行`）

**O1 · 各页「重置」语义不一致（本轮直接动因）**

- `JiaoLongControl/Client/src/pages/CPU.vue:184-194` —— 重置只 `Object.assign(CPUData.Custom, CPU_CUSTOM_DEFAULTS)` + `saveConfig()`，**不下发硬件**（注释自己写着「只改参数并存盘，不下发硬件」）。
- `JiaoLongControl/Client/src/pages/RyzenSmu.vue:363-372` —— 同上：只填表单 + 存配置，注释「重置 = 只改表单值并写回配置，不下发硬件」。
- `JiaoLongControl/Client/src/pages/Fan.vue:119-126` —— 重置走 `handleRestoreAuto()` → `stores/fan.ts:275-320`，**真下发**（停曲线 + `Fan.RemoveFanSpeed`）。
- `JiaoLongControl/Client/src/pages/GPU.vue:308-337` —— 重置调 `NvidiaGpu.ResetGpuClock()` / `ResetMemoryClock()`，**真下发**。

同一个词在四个页面上有两种含义，用户无法从界面判断「点了重置之后，硬件到底变没变」。

**O2 · 可逆性分级此前只是日志标签**

`src/domain/operations.ts:21-29` 定义了 a–e 五级可逆性，硬规则写着「只有 level === 'a' 才允许 UI 出现『回滚/撤销』字样」。
但全仓 `reversible: 'x'` 共 29 处（`src/` 内 25 处，另 4 处在 `src/domain/__tests__/operations.spec.ts`），**全部只写进活动日志**：

- `src/domain/cpuPowerPlan.ts:31`、`src/stores/mode.ts:217/232/254/287/298`、`src/stores/fan.ts:212/228/245/270/289/305/317`、
  `src/pages/CPU.vue:158`、`src/pages/GPU.vue:262/303`、`src/pages/RyzenSmu.vue:225/280/327/355`、
  `src/pages/KeyBoard.vue:193/238`、`src/composables/useFanCurveEditor.ts:133/145/403`

没有任何一处用它约束按钮。本轮把它变成真门禁：`src/domain/appliedFeatures.ts` 的 `removalBlockedReason()`。

**O3 · 前端配置类型缺 `Safety` 段**

- 后端模型有：`JiaoLongControl/Server/Core/Models/JiaoLongConfig.cs:13`（`Safety` 属性）与 `:22-45`（`SafetySection`：`WriteGateEnabled` / `ThermalWatchdogEnabled` / 四项看门狗阈值）。
- 前端类型没有：`JiaoLongControl/Client/src/types/config.ts:98-106` 只声明 `App/Cpu/Gpu/Fan/Log/Smu`。
- 设置页因此只能用字符串路径访问：`src/pages/Settings.vue:54-59` 传 `configPath: 'Safety.ThermalWatchdogEnabled'`，由 `src/components/common/SettingToggle.vue:43-50` 动态按路径取值（`:52` 兜底 `?? false`）。

运行时该字段确实在桥接返回的 JSON 里，所以开关值是对的；但**类型层面没有契约**——后端新增字段时前端不会报错，只能靠人记得同步。本看板直接从桥接 JSON 按路径取值（`readByPath`），不受这个类型缺口影响。

**O4 · 桥接「类型声明」与「运行时可调用面」不一致**

`src/utils/bridge.ts:149-292` 的 `BridgeApi` 是**类型声明**，真正导出给页面用的是同文件下方的包装对象：

| 声明里存在 | 包装对象里不存在 | 证据 |
|---|---|---|
| `Fan.SetMaxFanSpeedSwitch` / `GetMaxFanSpeedSwitch` | `Fan` 导出对象只有 `GetFanSpeed` / `SetFanSpeed` / `RemoveFanSpeed` | 声明 `src/utils/bridge.ts:168-169`，导出 `:456-460` |
| `RyzenSmu.SetTdcLimitMp1` / `SetTdcLimitRsmu` | `RyzenSmu` 导出对象无这两个方法 | 声明 `src/utils/bridge.ts:276-277`，导出 `:612-637` |

即：类型上「存在」、运行时调用会抛。本轮的注册表用例把这条做成了判别性反例（`resolveBridgeMethod(bridge, 'Fan.SetMaxFanSpeedSwitch') === null`），防止以后再出现「照类型抄一份名单」。

**O5 · 三个功能/字段在前端没有任何消费点**

- TDC 电流限制：配置模型有字段（`Server/Core/Models/JiaoLongConfig.cs:303-306`）、类型有声明（`bridge.ts:276-277`）、页面 `CONFIG_GROUPS` 没有（`src/pages/RyzenSmu.vue:40-97`）、包装对象也没有写方法（`bridge.ts:612-637`）。
- GPU 高级超频面板：整段被注释（`src/pages/GPU.vue:501-624`，含 `handleApplyAdvanced`/`handleResetAdvanced` 的按钮），写方法只剩声明（`bridge.ts:239-241`、`:577-583`）。
- 键盘灯效模式：灯效页只调用 `GetColor/SetColor/GetLightBrightness/SetLightBrightness`（`src/pages/KeyBoard.vue:60-75`、`:196-220`），`Keyboard.GetMode/SetMode`（`bridge.ts:182-183`）无人调用。

## 4. Hypothesis（含反证条件）

**H1 · 风扇「手动接管」的判定是推断（不是读出来的）**

`src/stores/fan.ts:20-22` 自己写明：EC 无法区分「固件自动」与「残留手动值」，手动判定为 Hypothesis；
`:154-157` 的实际口径是 `AutoFan.IsRunning() === false && config.Fan.ManualFanSpeed > 0`。
**反证条件**：若 EC 存在「手动转速掩码/手动值」查询命令，应以查询为准，并把 `fan.manual-speed` 行的「推断」标注改成直读。
看板照现有口径显示，但**显式打了「推断」标签**（`readback.kind = 'inferred'`），并且该行的移除结果只报「仅命令确认」，不报「已移除」。

**H2 · 「配置里是 0」不等于「硬件里是 0」**

SMU 限制型参数的配置默认值就是 0（`JiaoLongConfig.cs:279-318` 全部无初始值），而 0 同时是「未读取」的渲染值；
因此前端把 0 当「未设值」并拒绝写入（`src/domain/writeGate.ts:29-42` 的 `SMU_ZERO_UNWRITABLE`）。
**反证条件**：若实现 SMU 回读（`docs/KNOWN_ISSUES.md:133-136` 第 24 条：需要传输表协议 + 按 family 逐一真机验证），
「未读取」应改为真实读数，本假设作废。

**H3 · 看板的「不一致」在真机上的分布未知**

本轮所有「配置开着·硬件没写进去」都是假状态驱动出来的（mock 桥 + 单测），**没有一次真机复现**。
**反证条件**：真机上任一行的回读值与配置不符但硬件其实已生效（即 getter 口径不对），该行必须换 getter 或降级为「不可回读」。

## 5. Decision（本轮）

**D1 · 注册表是唯一真源，且可逆级别是真门禁**（负责人：实施者（AI），2026-10-05）
依据：本轮任务书硬规则 + v4 §8.2（禁止万能撤销）+ `src/domain/operations.ts:21-29` 的五级定义 + O2。
做法：`src/domain/appliedFeatures.ts` 声明 `id/名称/分组/意图路径/回读方法/可逆级别/移除步骤/结论+理由`；
`removalBlockedReason()` 对 `readback === null` 或 `reversibility === 'e'` 的项返回原因、`canRemove = false`；
组件只遍历注册表，**没有任何 if/else 功能清单**（加一行即多一行，有行数单测）。

**D2 · 「移除」的判据是写后独立重读，回读失败不算成功**（负责人：实施者（AI），2026-10-05）
依据：v4 §8.4 + §14.5（模式胶囊口径：命令被接受但回读未确认 ≠ 成功）。
做法：移除步骤走 `src/composables/useCompositeWrite.ts`，末尾追加显式「复核：独立重读 `<getter>()`」步骤；
重读失败或读到的仍是「生效」→ 该步 failed → 界面只能说「未确认移除成功」，**不得出现「已移除」**；
对无可靠回读的项（如风扇手动掩码）只报「命令已接受 · 无法确认」，并记入 `stores/activity.ts`（`outcome: 'accepted'`）。

**D3 · 本轮只出结论不删功能**（负责人：实施者（AI），2026-10-05）
依据：本轮任务书硬约束 2。`HomeCardType` 仍 8 项（`src/stores/index.ts:51-66`）、`PAGE_IDS` 未变（`src/stores/pageIds.ts:6-15`）、
`Server/**` 的 C# 源码零改动（探针 csproj 除外，见 §5 D4）。cut 只作为看板标签与本文档结论存在。

**D4 · 探针工程编译红灯的修法**（负责人：实施者（AI），2026-10-05）
依据：`RyzenSmuControllerTest` 编译报 CS0234 → 补齐 `Services\SmuWriteGate.cs` 后又暴露 CS0103
（`CommandResult.cs:36` 自 HEAD 起就引用 `LogRuntime.VerboseCommandLog`，而 `LogRuntime` 又依赖 `Models.LogSection`）。
做法：只在 `RyzenSmuControllerTest/RyzenSmuControllerTest.csproj` 里补 `Compile Include`（SmuWriteGate/LogRuntime/JiaoLongConfig/ConfigAttributes）
与 `PackageReference YamlDotNet 18.1.0`（与主项目一致）；**未改任何 .cs 文件**。
结果：0 错误（余 CS1668 机器级残留 + `Program.cs:251` 既有 CS0162 警告）。
