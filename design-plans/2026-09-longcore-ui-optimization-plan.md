# LongCore UI 优化计划

> 版本：v1.0 · 2026-09-21  
> 状态：Draft，待进入实现排期  
> 适用范围：`JiaoLongControl/Client` 的主壳、概览、CPU、GPU、风扇、键盘灯效与 Ryzen SMU 页面

## 1. 文档定位与证据边界

本计划根据用户提供的六张页面截图整理：

| 截图 | 页面 | 作为证据的内容 |
| --- | --- | --- |
| #1 | CPU 设置 | 自定义功耗与温度墙、滑条、实时状态、单页应用操作 |
| #2 | GPU 设置 | GPU 信息、频率控制、实时监控小卡片 |
| #3 | 风扇曲线编辑器 | 曲线编辑、启停、CPU/GPU 曲线切换、实时运行状态 |
| #4 | 风扇控制 | 手动接管、目标转速、恢复自动控制、安全提示、最近活动 |
| #5 | 键盘 RGB 灯效 | 灯效预览、颜色拾取、快速预设、亮度与渐变效果 |
| #6 | Ryzen SMU | 功耗限制滑条、未读状态、SMU 监测、术语解释 |

这些截图是当前界面的观察证据，不是设计要求。截图中的浅色主题、紫色曲线、英文标题、卡片尺寸和现有文案都不应被直接视为必须保留的规则。现有产品约定仍以 [DESIGN.md](/I:/JBCode/AI%20Tools/LongCore/DESIGN.md) 和 [UI重构_最终方案_v4.md](/I:/JBCode/AI%20Tools/LongCore/docs/UI重构_最终方案_v4.md) 为准；本计划负责把截图中已经暴露的界面问题整理为可执行的优化顺序，不重新定义协议、驱动或硬件安全边界。

## 2. 目标

LongCore 应该让用户一眼知道三件事：当前硬件处于什么状态、哪些参数可以调整、调整是否已经真正生效。界面需要从“多个页面的卡片集合”收敛为“同一台硬件仪器的不同操作面板”。

本轮优化的目标是：

1. 统一主壳、页面标题、卡片、控件和应用反馈的语法。
2. 区分观察值、待应用值、已应用值、不可读取值和错误状态。
3. 让高频任务可以快速完成：切换性能档位、恢复自动风扇、修改功耗限制、调整键盘灯效。
4. 让危险操作具有明确的接管状态、恢复入口和结果反馈。
5. 保留现有硬件仪表身份：读数优先、冷青强调、温度语义色、少装饰动画、无玻璃拟态和霓虹背景。

## 3. 评审结论

### 3.1 主问题一：页面结构一致，但信息层级没有统一

六个页面都使用“浅灰背景 + 白色卡片 + 大标题 + 两列内容”的基本骨架，学习成本不高；但各页面的主次关系不同：CPU 页面把滑条作为主体，GPU 页面把信息卡和监测卡分开，风扇页面把手动控制、曲线和安全提示拆成多个区域，SMU 页面又变成大量相同滑条的长列表。

这会让用户在不同页面之间反复寻找：当前状态在哪里、编辑区在哪里、应用按钮在哪里、风险提示是否影响当前操作。页面需要共享一个稳定的顺序：

1. 页面标题与一句话说明。
2. 当前硬件/策略状态。
3. 主要控制区或只读监测区。
4. 应用状态与结果。
5. 补充信息、术语和历史记录。

### 3.2 主问题二：写操作的“暂存、应用、结果”没有形成统一模型

CPU 页面底部只有一个应用按钮，GPU 页面也有应用按钮，SMU 页面却几乎每个滑条都有一枚“应用本组”或类似操作入口。风扇页面还存在手动接管、恢复自动控制和安全提示。不同页面的按钮数量和位置让用户难以判断当前修改是否已经写入硬件。

建议所有写操作都遵循同一套状态语言：

- **当前值**：最近一次可靠读取到的硬件值。
- **待应用**：用户刚刚修改、尚未发送的值。
- **应用中**：命令已发出，正在等待结果。
- **已接受 / 已生效 / 仅命令确认**：根据是否能可靠回读，使用不同文案。
- **部分应用 / 失败 / 过期**：明确说明影响范围和下一步动作。

只有真正可安全逆转且有可靠读取值的操作才能叫“撤销”。风扇手动接管应提供“恢复自动控制”，SMU 无可靠 getter 时应使用“仅命令确认，不可回读”，不应伪装成完整成功。

### 3.3 主问题三：监测图表和说明承担了过多装饰，缺少决策信息

风扇曲线编辑器的紫色面积图有较强视觉存在感，但页面没有在同一视线内说明当前曲线是否启用、当前由谁控制，以及曲线修改是否已应用。风扇控制页面的实时图将 CPU、GPU、风扇等信息放在一个较小区域，安全提示却使用较长散文，重要程度不够清楚。RGB 页面使用真实感较弱的通用键盘网格，SMU 页面则展示了大量“未读取”值。

图表和状态卡应优先回答一个问题：用户现在是否需要采取动作。不能可靠读取的指标应显示为“未读取 / 不可用 / 过期”，不能用 0 代替；图表的颜色用于区分数据系列，温度告警颜色仍由温度语义源统一决定。

## 4. 目标信息架构

一级入口建议保持硬件领域型，不重新增加页面数量：

- **概览**：性能档位、CPU/GPU 温度、风扇、功耗和最近趋势。
- **性能**：CPU、GPU 的设置与实时状态，使用稳定的页面内分区。
- **散热**：风扇手动控制、自动控制、曲线编辑和安全状态。
- **灯效**：键盘 RGB 预览、颜色、亮度、预设和效果。
- **高级**：Ryzen SMU 等高风险、低频使用功能。
- **系统**：应用设置、设备信息、日志和诊断。

CPU 与 GPU 不必分别占据主导航入口；它们可以作为“性能”页面下的稳定分区或页面内标签。SMU 不应出现在高频入口中，但需要保留清晰的高级警示。现有窄图标轨可以继续使用，必须补充 tooltip 或展开标签，并保持选中态、分组和顺序一致。

## 5. 页面优化计划

### 5.1 主壳与导航

- 保留窄图标轨和顶部窗口栏，统一所有页面的内容起点、左右边距和滚动方式。
- 页面标题使用统一的字号和行距；副标题只说明当前页面能做什么，不放过长的实现细节。
- 导航按“监控 / 调节 / 设备 / 设置”分组，图标只负责识别，tooltip 负责解释。
- 检查底部设置图标和其他齿轮入口是否重复；确认后只保留一个权威入口。
- 主操作区使用统一的 `ApplyBar` 或同类组件，避免每个页面重新设计按钮位置。

### 5.2 概览页

- 顶部只放当前性能档位和紧凑状态，不重复显示 CPU、GPU、风扇数据。
- 性能档位需要区分“用户选择的配置”和“硬件实际观察到的档位”，切换后不能先乐观改变选中态。
- 主指标建议为 CPU 温度、GPU 温度、风扇、功耗四项；静态 CPU 型号、GPU 型号、内存和系统版本移入设备信息区域。
- 温度历史增加 `2 分钟 / 10 分钟 / 1 小时` 范围，显示当前值、峰值和异常区间。
- “估算功耗”必须在数值旁明确标记数据来源；不存在传感器时不能给出看起来像精确读数的格式。
- 首页下方空白区域优先用于模式说明、快捷操作和风扇控制状态，不继续增加装饰图表。

### 5.3 CPU 设置

- 将“核心设置”分为功耗限制、温度墙、频率与睿频三组，减少连续滑条造成的长表单感。
- 每组只保留一个应用区，顶部显示“当前值 / 待应用数量 / 配置来源”。
- 滑条右侧的数值使用等宽数字，并始终显示单位、范围和步进。
- 实时状态卡继续放在右侧，但只展示能帮助判断修改结果的指标：频率、电压、使用率、温度。
- 对温度墙、功耗限制和核心电压偏移等高风险参数，在控件附近提供短提示；详细解释放入可展开区域。
- 应用后逐项报告成功、失败、跳过和不可回读项，避免只显示一个总体成功消息。

### 5.4 GPU 设置

- 顶部保留 GPU 型号、驱动版本、显存容量和总线宽度，但降低静态信息的视觉权重。
- 频率控制区使用与 CPU 相同的“当前值—控件—应用状态”结构。
- 实时监测卡片统一尺寸和信息密度；小图表只保留真实有用的趋势，不用空白面积撑高卡片。
- 独显 / 混合输出等需要重启的状态，在控件旁直接显示“重启后生效”，不要把命令发送成功渲染成已经完成。
- GPU 温度、风扇转速、核心频率等系列颜色可以区分数据，但不能抢占冷青主操作色，也不能与温度危险色混淆。

### 5.5 风扇控制与曲线编辑

- 风扇控制页将“当前策略”放在最醒目位置：自动、手动接管或曲线控制，并说明当前由谁接管。
- 手动接管时保留常驻的“恢复自动控制”入口；安全说明改为短提示 + 可展开详情。
- 目标转速使用大读数、范围、步进和当前应用状态组成一个完整控制模块。
- 曲线编辑器顶部明确 CPU/GPU 曲线、启用状态、最后应用时间和当前策略；曲线拖动需要即时跟手，应用后给出结果。
- 实时遥测图放在控制区旁边，显示采样间隔、最近数据状态和关键读数；不使用假波形或无限装饰动画。
- 最近活动只记录用户能理解的操作，例如“手动接管”“恢复自动”“应用 CPU 曲线”，自动看门狗的底层写入不能淹没用户记录。

### 5.6 键盘 RGB 灯效

- 预览应尽量使用真实键盘布局或明确标注为“区域预览”；通用矩形网格容易让用户误以为每个按键都能独立控制。
- 颜色拾取、RGB 数值、亮度级别和当前方案应放在同一个“当前方案”区域。
- 快速预设使用统一的选中态、名称和颜色样本；预设点击后先预览，应用或保存后再写入硬件。
- 灯效动画需要显示启用状态、速度和停止后的行为；静态颜色和动画预览不要使用相同的状态表达。
- 保留“应用”后持久化的语义，避免颜色预览变化被误认为已经写入硬件。

### 5.7 Ryzen SMU

- 将页面标记为“高级 / 高风险 / 仅命令确认”，在标题下用一句话说明读回限制。
- 功耗限制按 STAPM、Fast、Slow、PPT、电流等领域分组，减少同款滑条的连续堆叠。
- 删除每一条参数旁重复的应用按钮，改为按组暂存、统一应用，并在底部显示逐项结果。
- “未读取”是明确状态，不显示为 0；输入框、滑条和状态徽章要能区分目标值、当前未知值和命令结果。
- 右侧实时卡片只保留能可靠读取的数据；术语解释放入折叠区，避免正文被解释文字切碎。
- 应用失败或部分成功时，显示具体参数和下一步动作；不提供没有依据的“撤销”按钮。

## 6. 视觉系统执行规则

本计划沿用现有设计系统的主要方向：中性背景、实心面板、冷青主强调色、温度语义色、数值等宽字体、4–8px 小圆角、1px 分割线和克制动效。

执行时遵守以下规则：

- 先修信息层级和操作模型，再决定是否更换整套主题；浅色截图不能单独证明需要重新做深色主题。
- 主操作、选中态、焦点环和统一进度条使用同一冷青色。
- 温度告警遵循已有 `temperature.ts`，不在页面中复制阈值。
- 紫色、绿色等颜色只作为数据系列或 RGB 内容的一部分，不能回到全局主色或渐变按钮。
- 读数更新即时显示，不使用持续闪烁、假波形、无限脉冲或整页位移动效。
- 数值使用等宽字体和 tabular numbers；单位与数值保持紧密但清楚的层级。
- 卡片高度由内容决定，避免为了对齐而让空卡片撑出大块空白。

## 7. 执行顺序

### Phase 0：证据和基线

整理六张截图对应的页面、窗口尺寸、DPI、主题和硬件状态；确认当前工作树和现有 `DESIGN.md`、`docs/UI重构_最终方案_v4.md` 的关系。此阶段只补证据，不修改产品代码。

**出口条件：** 页面清单、当前状态模型、截图证据表和未决问题已经记录。

### Phase 1：主壳与共享组件

统一 `PageShell`、页面标题、副标题、导航 tooltip、卡片层级、读数头、状态徽章和 `ApplyBar`。先完成一个空数据或只读页面的视觉迁移，确认不会影响窗口、滚动和导航。

**出口条件：** 所有页面具有相同的内容起点、标题语法和应用反馈位置。

### Phase 2：风扇垂直切片

以风扇控制页为第一条完整链路，跑通自动 / 手动 / 曲线三种策略、危险提示、恢复自动、实时监测、应用结果和最近活动。风扇页面同时验证新的状态徽章、图表和安全提示。

**出口条件：** 用户能够独立完成“降低风扇转速、恢复自动控制、确认当前由谁控制”三项任务，且不会把过期或失败读数当成真实 0。

### Phase 3：概览、CPU、GPU

将概览页的重复读数和空白区域收敛，再把 CPU/GPU 迁移到相同的控制模块语法。此阶段重点验证“选中的配置、实际硬件档位、待应用值”不会混淆。

**出口条件：** 用户能在 3 秒内读出当前档位、CPU/GPU 温度和风扇状态，并能理解一次修改是否已经生效。

### Phase 4：键盘灯效与 Ryzen SMU

键盘页重点处理预览与应用语义；SMU 页重点处理高风险提示、未读状态、按组应用和部分成功结果。两页不应为了统一而牺牲各自的操作特点。

**出口条件：** 灯效预览不会冒充硬件已应用；SMU 的未知值、命令确认和失败结果清晰可区分。

### Phase 5：视觉收口与验证

进行主题、颜色、图表、焦点环、键盘操作、reduced-motion 和 DPI 验收。至少覆盖 100%、125%、150%、175%、200% 文本缩放，以及目标 2560×1600、150% 场景。检查长文案、错误提示和底部应用区是否可达。

**出口条件：** 通过主任务清单、状态真实性检查、窗口可达性检查和前端构建验证。

## 8. 验收清单

- [ ] 概览页不重复显示同一个 CPU/GPU/风扇读数。
- [ ] 用户能看懂性能档位、硬件实际状态和待应用配置之间的区别。
- [ ] 手动风扇接管时，当前控制者和恢复自动入口始终可见。
- [ ] 读取失败、过期、不可用和未读取不会渲染成真实 0。
- [ ] CPU/GPU/SMU 使用统一的待应用、应用中、结果反馈模型。
- [ ] SMU 不再为每一条滑条放置重复的应用按钮。
- [ ] 图表显示采样范围、数据状态和有意义的趋势，不使用装饰性假波形。
- [ ] 键盘 RGB 预览、快速预设和硬件应用状态彼此区分。
- [ ] 主操作使用冷青，温度颜色使用唯一权威来源，紫色不回到全局强调层。
- [ ] 窄导航在没有文字的情况下仍可通过 tooltip 识别。
- [ ] 目标 DPI 和窗口尺寸下，页面滚动、底部按钮、焦点环和错误消息都可访问。

## 9. 未决问题

以下问题不应在实现中靠猜测解决：

1. 浅色截图与现有近黑硬件仪表身份之间，最终默认主题是否需要重新验证；第一阶段先按主题无关的结构问题处理。
2. 键盘实际布局是否有可用的硬件映射；没有映射时必须明确称为区域预览。
3. Ryzen SMU 各字段的可靠 getter 范围；在确认前统一按“仅命令确认，不可回读”设计。
4. GPU 输出模式、风扇策略和功耗设置的生效时机；需要重启或只能恢复默认的操作，必须在 UI 中如实表达。

## 10. 与现有计划的关系

本计划是截图评审后的执行补充，不替代 [docs/UI重构_最终方案_v4.md](/I:/JBCode/AI%20Tools/LongCore/docs/UI重构_最终方案_v4.md) 的状态真实性、安全边界、领域模型和 IA 验证要求，也不重新打开协议层或驱动层决策。实现前应先检查两份文档是否出现冲突；如果冲突涉及状态语义或安全行为，以现行 RFC 和代码证据为准，如果只涉及视觉排列，则以本计划的页面优化顺序为执行参考。
