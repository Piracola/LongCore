# 08 · 硬件安全架构

> 目标：**让上层的任何 bug 都无法把硬件推入不可逆的危险状态。**
> 本文先给出诚实的物理风险排序（第 1 节），再盘点全部写入通道与缺口（第 2 节），
> 然后给出分层防御架构（第 3 节）、本轮已落地项（第 4 节）、建议的下一步（第 5 节），
> 最后是"如何避免再次出现 Bug 1 / Bug 2 那类奇怪故障"的工程约定（第 6 节）。

---

## 1. 结论先行：真实的物理风险排序

先纠正一个直觉误区：**"足够底层"不等于"容易烧硬件"。**

蛟龙 16 Pro 上有多层硬件级自保护，软件绕不过去：

| 保护 | 触发 | 软件能否绕过 |
|---|---|---|
| PROCHOT / 热节流 | CPU 约 100 °C 强制降频，更高则断电 | 不能 |
| VRM 过流/过温保护 | 供电模块超限即限流 | 不能 |
| EC 自身 thermal table | 自动模式下风扇曲线由 EC 独立掌控 | 能（手动模式会接管） |
| 电池充放电保护 | 由 EC/充电芯片独立管理 | 不能 |

所以：**功耗/频率/电压参数写错 → 降频、重启、蓝屏，重启即恢复，属于可逆故障。**
真正值得死守的窗口只有三个，按严重度排序：

### 🔴 高 — EC 寄存器被写到错误的地址
命令码算错、地址算错，可能破坏 EC 里键盘、电源键、充电逻辑相关的状态。
这类故障**不随重启恢复**，严重时需要售后刷写 EC —— 这才是本项目"不可逆"风险最高的一项。
→ 对应防御：**命令白名单 + EC 地址白名单**（第 3 节 L1）。

### 🔴 高 — 手动风扇模式下散热失效
`0xB20` 手动掩码置位后，风扇转速被软件钉死，**EC 自身的温控曲线被绕开**（见上表唯一"能绕过"的一行）。
转速 0 或过低 + 满载 = 持续高温。硬件会降频自保，但长期高温加速老化，且若 EC 状态同时异常则失去兜底。
→ 对应防御：**转速 0 硬性拒绝 + 上下限钳制 + 崩溃恢复护栏**（第 4 节）。

### 🟡 中 — SMU 过压
Curve Optimizer 正值 / VoltageBoost 属于加压。加压 + 高温会加速电迁移。
SMU 自身有保护，但这是软件能直接触及的最"电气"的一层，应当单独设闸。
→ 对应防御：**尚未实现**，见第 5 节。

**其余全部可逆。** 明确这一点很重要：不必追求"任何 bug 都不碰硬件"，
只需把上面三条堵死，其余保证"重启可恢复"即可。

## 2. 现状盘点：五条写入通道

| # | 通道 | 唯一出口 | 现有护栏 | 缺口 |
|---|---|---|---|---|
| 1 | WMI / EC 命令（8..23） | `MethodServices.SetValue` ×2 | 锁串行化 | ❌ 无白名单 / ❌ 无值域 / ❌ 无限流 / ❌ 无审计 |
| 2 | EC 寄存器直写 | `Blding64.ThrottledWrite` | ✅ 地址白名单(4个) ✅ 300ms 同值节流 ✅ `EcGuard` 崩溃恢复 | ❌ 转速 0 未禁 / ❌ 上限未校验 |
| 3 | SMU（PawnIO 内核驱动） | `RyzenSmuController.Send` | — | ❌ 全裸 |
| 4 | NVAPI（GPU 超频/风扇/温度策略） | `NvApiOverclock` | 局部 | ❌ 无统一校验 |
| 5 | `powercfg`（电源计划） | `PowerController.RunPowerCfg` | — | 🟢 OS 级，完全可逆，低危 |

### 已存在的好设计（不要重复造）
- `Blding64.WritableAddresses`（`Blding64.cs:44`）——EC 地址白名单，写的注释就是正确的安全思路。
- `Blding64.ThrottledWrite`（`:56`）——同值 300ms 节流，且**只有底层写成功才记入缓存**，避免失败写入被误判完成。
- `EcGuard`（`Server/Core/Services/EcGuard.cs`）——心跳文件 + 崩溃后恢复风扇自动模式。这个模式值得推广到其他持久状态。

### 三个此前未被发现的缺口（本轮修正）

1. **`MethodServices.SetValue` 零校验**（`MethodServices.cs:30`）
   `Convert.ToByte(value)` 直接转换，超范围抛 `OverflowException` 并穿透到 COM 边界；
   命令码本身完全不受限——**可以往任意命令码写任意值**。这是最宽的口子。

2. **`ConfigRange` 从未被强制**
   `ConfigSerializer.cs:130` 读取该属性**只是为了往 YAML 里写一行注释**（`范围: 5 ~ 120`）。
   也就是说：手改 `config.yaml` 就能让任意越界值直达硬件，前端滑块是唯一防线。

3. **风扇转速零钳制**
   `FanController.SetFanSpeed(byte)` 原样下发裸 byte；前端滑块 `:min="0" :max="8000"`，
   经 `bridge.ts:383` 的 `fanSpeed / 100` 变成 0–80 —— 而 EC 规格上限是 **68**（单位 100 RPM）。
   即 **0（停转）和 69–80（越界）都能从 UI 直接发出**。`toByte()` 也只校验整数性，不钳制。

## 3. 分层防御架构

```
L0  单一真源      —— 范围只声明一次（[ConfigRange]），UI/配置/写入闸门共用
L1  写入闸门      —— 命令白名单 + 值域 + 限流 + 审计（唯一出口处拦截）
L2  崩溃恢复      —— 心跳证据 + 下次启动回滚安全态（EcGuard 模式推广）
L3  过温看门狗    —— 运行中持续监视，越限强制回安全态
L4  启动安全模式  —— 配置异常时以默认配置启动，不下发
```

设计原则：

- **拒绝，而不是静默钳制。** 静默改写会把"下发了错误的值"变成看不见的事，掩盖 bug。
  唯一例外是配置载入阶段（L4），那里拒绝会导致功能整体不可用，改为收敛到边界值 + 告警。
- **闸门放在唯一出口，而不是散落各处。** 改一处即全覆盖，也不会被新增调用点绕过。
- **每层都要有逃生舱。** 安全阀值判断有误时，用户能不重新编译就放行（否则安全机制会变成故障源）。

## 4. 本轮已落地

### 4.1 硬件写入闸门 `HwWriteGate`（新建）
`Server/Core/Services/HwWriteGate.cs`

挂在 `MethodServices.SetValueCore`（两个重载汇流后的唯一出口），**零调用点改动即覆盖通道 1 全部写入**。

| 闸 | 内容 |
|---|---|
| 命令白名单 | 仅允许实测被写入的 8 个命令码：`SystemPerMode(8)` `GpuMode(9)` `Ambientlight(15)` `RGBKeyboardMode(16)` `RGBKeyboardColor(17)` `RGBKeyboardBrightness(18)` `MaxFanSpeedSwitch(20)` `CPUPower(23)`。其余（含 `UnKnow(255)`）一律拒绝并记 Warn。 |
| 载荷值域 | `SystemPerMode` 0–2（**3=Custom 是本地逻辑态，固件命令 8 不认识，禁止下发**）、`GpuMode` 0–1、`Ambientlight` 0–1、`RGBKeyboardBrightness` 0–3、`MaxFanSpeedSwitch` 0–1；`CPUPower` 按子命令：SPL 5–120 W、SPPT 5–150 W、温度墙 60–105 °C。范围取自 `[ConfigRange]` + `docs/02_协议手册.md §6`，与二者一致。 |
| 写入限流 | 令牌桶。单命令突发 5 次、稳态 3 次/秒；全局突发 20 次、稳态 10 次/秒。自激循环通常是数十次/秒，会被直接掐断——**这条闸就是 Bug 1（一次按键连切十几次）的物理兜底**。 |
| 审计日志 | 下发记 Debug，拒绝记 Warn（含命令码、载荷、原因）。 |

逃生舱：`HwWriteGate.Configure(bool)` / 静态 `Enabled` 字段，供配置开关接管。

附带修正：`SetValue(MethodName, object)` 中 `Convert.ToByte` 的 `OverflowException`
改为干净返回 `false` + 日志，不再穿透到 COM 边界。

### 4.2 封堵风扇停转通路（通道 2）
`Server/Core/Drivers/Blding64.cs`

新增 `ValidateFanSpeed(byte, string)`，在**最底层**（`CpuFanSetSpeed` / `GpuFanSetSpeed`）拦，
因此自动风扇曲线等所有调用者一并覆盖：

- `speed == 0` → **硬性拒绝** + Error 日志。手动模式 + 停转 = 绕开 EC 温控，唯一现实的损伤路径。
- `speed > 68` → 拒绝（EC 规格上限，超出行为未定义）。
- `speed < 15`（1500 RPM）→ 放行但记 Warn。

配套改动：
- `CpuFanSetSpeed` / `GpuFanSetSpeed` 返回类型 `void` → `bool`，
  `FanController.SetFanSpeed` 如实回传结果 —— 否则护栏拒绝后前端仍显示"设置成功"。
- `AutoFanControl.MIN_FAN_BYTE` 由 0 改为 15，避免曲线算出 0 时被护栏静默拒绝。
- 前端 `pages/Fan.vue` 滑块 `0–8000` → `1500–6800`，对齐 EC 规格。
- `JiaoLongConfig.ManualFanSpeed` 补 `[ConfigRange(1500, 6800)]`。

### 4.3 `ConfigRange` 真正生效（L0 / L4）
`Server/Core/Utils/ConfigSerializer.cs`

`Load()` 返回前统一执行 `EnforceRanges()`：反射递归下探（最深 4 层），
把带 `[ConfigRange]` 的数值属性**收敛**到声明范围并记 Warn。
支持 `int/long/short/ushort/uint/byte/float/double`；跳过字符串、值类型与集合。

这里刻意用"收敛"而非"拒绝"：启动阶段拒绝配置会导致功能整体不可用，
收敛到边界值更稳妥，且留有日志痕迹。

## 5. 建议的下一步（待定夺，本轮未实现）

### 5.1 过温看门狗（L3）——建议实现
独立 1 秒轮询，与 UI 和用户配置解耦：

- CPU 或 GPU 温度 ≥ 95 °C 持续 10 秒 → 强制回安全态：
  恢复风扇自动模式（`RemoveFanSpeed`）+ 关闭自定义功耗子状态 + 切静音模式。
- 带回滞，恢复阈值 85 °C，避免抖动。
- 动作必须记 Error 日志并弹提示，让用户知道"软件接管了"。

**需要你定夺**：看门狗是否应覆盖用户显式设置的手动转速？
我倾向"覆盖"——但那会推翻用户的显式意图，属于产品决策，故本轮未擅自加入。
建议做成默认关闭、`Safety.ThermalWatchdogEnabled` 开关，先小范围试用。

### 5.2 启动安全模式（L4）
- 配置解析失败 / 关键值缺失 → 以默认配置启动并提示，不下发任何硬件写入。
- "上次异常退出"标记（复用 `EcGuard` 的心跳思路）→ 本次启动只恢复安全态，不自动应用自定义功耗。

### 5.3 自定义功耗子状态的崩溃恢复（L2）
目前只有风扇手动模式有 `EcGuard`。自定义功耗子状态（命令 23 `OpenState`）同样跨进程存活，
进程被强杀后 EC 会停在自定义功耗态。建议按 `EcGuard` 同构补一份护栏。

### 5.4 SMU / NVAPI 通道闸门（通道 3、4）
把 `HwWriteGate` 的思路推广：
- SMU：Curve Optimizer 限制在负值区间（**禁止正偏移=加压**），或至少对正值加二次确认。
- NVAPI：`SetThermalPolicy` 的温度上限、`ChangePstatesLevel0Settings` 的 0–200 MHz 偏移范围校验。

## 6. 工程约定：如何避免再次出现 Bug 1 / Bug 2 那类故障

这轮两个 bug 都不是"手滑写错"，而是**结构性问题**。针对每类定一条硬约定：

| 故障模式 | Bug | 约定 |
|---|---|---|
| **事件回写闭环** | 热键事件 → `Set` → 固件再抛同一事件 → 无限循环 | 固件事件**只镜像，不回写**。事件已携带目标状态时，客户端只更新 UI 与联动项。判定依据：官方实现 `decompiled/main.cs:2177` 也是只改 UI。 |
| **缺前置状态** | 未 `OpenState` 就下发 SPL/SPPT/温度墙，写入被 EC 拒绝 | 有前置依赖的下发，必须在**同一函数内**显式完成前置步骤；协议顺序以官方实现为准，不靠推测。 |
| **可选步骤致命中止** | Curve Optimizer 失败 → 整个应用流程 `return` | 区分**致命/非致命**步骤。可选能力失败只告警，不回滚已完成的主流程。 |
| **范围多处声明** | 前端 0–8000 / 后端 5–120 / EC 68 | 范围**只声明一次**（`[ConfigRange]`），UI、配置载入、写入闸门共用同一真源。 |
| **前端是唯一防线** | 滑块 min/max 可被绕过，`toByte` 不钳制 | 前端范围只作输入体验，**后端必须独立校验**。 |
| **异常穿透边界** | `Convert.ToByte` 抛异常到 COM | 跨 COM/WebView 边界的入口统一 try/catch，转为结构化失败。 |
| **注释即"已实现"** | `[ConfigRange]` 只生成注释，从未校验 | 声明式属性必须有对应的强制执行点，否则等价于没有。 |

### 实机回归清单（每次发版前）
1. Fn 性能键按一次 → 只切一档、只弹一次 OSD。
2. CPU 自定义档改参数 → 应用成功，首页档位胶囊变"自定义"。
3. 风扇手动模式 → 拉到最低仍是 1500 RPM，无停转；退出应用后风扇回自动。
4. 强杀进程（`taskkill /F`）→ 重启后风扇自动模式恢复。
5. 手改 `config.yaml` 写入越界值 → 启动日志出现"配置越界已收敛"，硬件值仍在范围内。
